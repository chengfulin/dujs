## 1. 方法

1. 以 sparse checkout 取得 `mdn/content` 的三個模組目錄，以及完整的 `mdn/learning-area`（blobless、unshallow，用來查每個檔案最後的 commit）。
2. 用腳本解析每篇 `index.md`：找出 `{{EmbedLiveSample("id")}}`，再收集該 id 的程式碼：用 `live-sample___<id>` 標記的 fence（同一個 fence 可以帶多個 id），或者沒有標記時，取 slug 為 `<id>` 的 heading 底下所有的 fence。HTML fence 裡的 `<script>` 也一併收集。沒有被任何 live sample 用到的 `js` fence 歸為「內嵌片段組」，每篇文章算一組，排除 `example-bad`。
3. 用 dujs 自己的 espree（script 解析失敗時改用 module 解析）＋eslint-scope 做 AST 特徵偵測：ES 語法、瀏覽器 API（以 regex 判斷）、以及和 dujs 限制對應的模式：
   - callback 傳給 `forEach`、`map`、`then`、`setTimeout`、`setInterval`、`requestAnimationFrame` 等 → README「Anonymous function call」
   - 自訂函式的呼叫不是呼叫敘述 → README「Only call statements…」
   - 巢狀函式讀外層函式的區域變數 → README「Closure」
   - `catch (e)` → README「catch parameters」
   - instance field → README「Instance field initializers」
   - `x.onclick = …` → 只辨識 `addEventListener`
   - `this`、`class`、`prototype` → README「Object properties, this」
   - 決策條件中，巢狀 Binary、Call、Unary 運算式之後才讀到的識別字（`&&`、`||`、`?:` 會先拆開）→ §20
   - `new X();` 當成敘述 → §21
   - 呼叫 class 方法 → §7
   - 函式本體含 `switch`、`for-in`、`for-of` → §18
   - 預設值是函式 → §10
4. 分類規則（**是靜態啟發式判斷，不是 dujs 的實跑結果**；抽查過 `image_gallery` 的 gallery-finish 與 web-storage 的 `index.js`）：
   - **A 可完整分析**：只觸及 README 的「assigning to `a.b` defines `a`」約定，以及「HTML DOM object」（DOM 只當 I/O：查到元素後存進變數、寫屬性輸出）。在 dujs 文件化的模型下，每個 pair 都能人工完整推導。
   - **B 可分析但有已知限制**：另外觸及 README Limits 的其他條目，或尚未修的 §n。依據欄會列出觸及的條目。
   - **C 目前無法分析**：解析失敗（刻意寫錯）、沒有 JS、執行環境不是頁面（service worker）、入口由外部函式庫回呼驅動，以致幾乎沒有函式會被連結，或程式刻意寫錯而沒有明確的期望行為。
5. 腳本放在 [`tools/`](tools/)（`feat.js`、`extract.js`、`gen.js`、`lafeat.js`），可以重跑；中間資料 `out/rows.json` 等未保存（重跑腳本即可產生）。

## 3. 範例清單與分類

欄位說明：
- **類型**：Live 是文章內嵌的 live sample；TYS 是 Test your skills 題目，「(+-finish)」表示同一題另有解答 sample，分類以解答版為準；Challenge 是挑戰題；Repo 是 learning-area 的完整範例檔；Snippets 是文章內嵌片段的彙總。

- **執行需 HTML/CSS**：指範例在瀏覽器裡跑需不需要 HTML/CSS。dujs 只吃 `-js` 檔，分析不需要 HTML，但 `<script>` 要先抽出來。

- **層級**：ES5、ES2015（含 ES2015–ES2016），或 ES2017+（async/await、`??`、class field 等）。
- 每篇文章的最後修改 commit（GitHub API `commits?path=`）見附錄 A。

## 4. 語言功能與 API 涵蓋觀察

- **語法**：這三個模組幾乎都是 ES2015 的寫法（`const`/`let`、箭頭函式、template、`for-of`）。ES2017+ 只出現在下列範例，`generator`、模組 `import`/`export`、optional chaining、logical assignment、private field 在**可執行範例中都沒有出現**：
  - `heroes-finished*.html`、`github-search`、json 文章片段：async/await
  - `github-search`：`??`
  - oojs TYS、classes 片段：class field、`#private`
  
  只靠這三個模組，無法驗證 dujs README「Supported syntax」宣稱的多數 ES2015+ 功能，需要其他語料補足（見 §5.4）。
- **語意上 dujs 有建模的瀏覽器機制**：
  - `addEventListener` 註冊（具名函式、函式運算式、箭頭函式都可以）→ intra-page 的事件 handler
  - `localStorage.setItem` → storage 節點（`lib/dujs/globalscopectrl.js` 的 `localStorageSetterNames = ['setItem']`）
- **沒有建模的機制**（全部歸入 README 的「Anonymous function call」，或「HTML DOM object」及 a.b 約定）：
  - `on*` 屬性 handler
  - Promise `then`/`catch` callback
  - `setTimeout`、`setInterval`、`requestAnimationFrame` 的 callback
  - IndexedDB 的 request 物件（不過 learning-area 的 IDB 範例都用 `addEventListener`，所以 handler 本身仍會被連結）
  - service worker
  - `localStorage.removeItem`、`clear`
  - 第三方函式庫（three.js、Google/YouTube API）
- **非決定性 API**（`Math.random`、`fetch`、計時器、媒體事件、`getUserMedia`）**不影響 dujs**：dujs 是靜態分析，期望的 pair 只取決於原始碼。只有日後要用動態執行驗證 pair 時，才會碰到這個問題。

### 5.2 怎麼保存

建議用「**以腳本抓取＋釘選 commit＋逐字落地**」的混合做法：

1. 在 `tests/fixtures/mdn/manifest.json` 逐筆記錄：`id`、`module`、`article URL`、`repo`（content 或 learning-area）、`commit SHA`、`path`、`live-sample id` 或行範圍、`sha256`、`license: CC0-1.0`、`needsHTML`、`classification`、`knownIssues: ["§20", ...]`。
2. 寫一支抽取腳本，邏輯同本次的 `tools/extract.js`：從 `raw.githubusercontent.com/<repo>/<sha>/<path>` 取檔，依 `live-sample___<id>` 或 heading 把 fence 拼起來，抽出 HTML 中的 `<script>`，寫成 `tests/fixtures/mdn/<module>/<id>.js`。**產出的檔案要 commit 進 repo（逐字），測試時不連網**；腳本只在更新時使用。
3. 不存 HTML/CSS（dujs 不需要）。manifest 記下對應 HTML 的 URL 就好。
4. 加一個檢查：fixture 的 sha256 必須和 manifest 一致，防止有人手改 fixture。

只逐字複製不寫腳本，日後要追上游更新會很難；只用腳本執行期抓取，測試會依賴網路、也不穩定。所以兩者都要。

### 5.3 期望結果怎麼產生

建議分兩段：「先鎖定現況，再逐案審核」，人工推導集中在小範例：

1. **鎖定**：沿用 `tests/golden` 的機制（`UPDATE_GOLDEN=1`、manifest 的 sha256），把每個 fixture 四種模型的 `.dupairs.dot` 存成 golden。這一步只能偵測「結果有沒有變」，不能證明結果正確。
2. **審核**：
   - A 類且 ≤ 35 行的範例（第一批的 #1–#4、#9）：**人工完整推導** pair，寫成斷言（類似 `tests/helpers/analyze.js` 的 pair 斷言）。
   - 其他範例：人工推導「關鍵 pair」，例如 handler 之間的全域變數、§20 的 p-use、storage 流。
3. **已知差異**：如果人工推導的正確 pair 和 dujs 現況不同，而且原因是 §n 或 README 限制，就在 manifest 的 `knownIssues` 記下來，並把斷言標成「預期失敗」（xfail）。之後修好 §n 時，斷言自動轉綠，golden 的 diff 也有依據可以審。004 修 §20、§7、§21 時，#6、#13 就可以這樣用。
4. 不要只靠現況 snapshot 當期望值，那是循環論證。至少要有一部分 pair 是人工推導、獨立於工具的。

### 5.4 隨 JS 標準更新擴充

- **追蹤上游**：寫一支腳本，比較 manifest 的釘選 SHA 與上游 HEAD（`git diff <sha>..HEAD -- <paths>`，或用 GitHub API `commits?path=`），列出有變動的範例。人工決定要不要升版；升版時重新抽取、重審期望值，並在 commit 中記錄差異。
- **偵測新語法**：對新抓到的程式跑特徵偵測（本次的 `feat.js`），找出 dujs README「Supported syntax」沒有列的語法。dujs 用 espree `ecmaVersion: 'latest'`，新語法要先升級 espree 才能解析。
- **補語料**：MDN Learn 的教材很少跟上新標準，要另外補：
  - MDN JavaScript Reference 頁面的範例（同樣在 `mdn/content`，同樣是 CC0；原本的 `interactive-examples` 已併入 content 的 `interactive-example` 區塊）
  - 需要更完整的語法覆蓋時，再考慮 test262（BSD 授權，要附授權聲明）
- **覆蓋矩陣**：在 manifest 加 `features` 欄，維護「語法／API × fixture」的覆蓋表，讓新標準的缺口一眼看得出來。
